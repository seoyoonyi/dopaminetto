# 이슈 작업 문서화 규칙

> 이슈 단위 작업에서 spec, plan, troubleshooting 문서를 자동으로 남기는 규칙이다.

---

## 1. 적용 대상

다음 작업은 사용자가 별도로 문서 생성을 요청하지 않아도 이 규칙을 적용한다.

- GitHub 이슈 작업
- PR 리뷰 대응
- 버그 수정
- 기능 추가
- 기존 기능의 동작 변경
- 재현, 원인 분석, 해결 과정을 남겨야 하는 작업

다음 작업은 자동 문서화 대상에서 제외한다.

- 단순 질의응답
- 커밋 메시지 추천
- 짧은 문구 수정
- 코드 변경 없이 상태만 확인하는 작업
- 사용자가 문서 생성을 원하지 않는다고 명시한 작업

---

## 2. 기본 문서 3종

이슈 단위 작업을 진행할 때는 다음 문서를 생성하거나 갱신한다.

| 문서            | 저장 위치                                                         | 목적                                                       |
| --------------- | ----------------------------------------------------------------- | ---------------------------------------------------------- |
| Spec            | `docs/specs/YYYY-MM-DD-<issue-slug>-spec.md`                      | 문제, 목표, 기대 동작, 비범위, 검증 기준 정의              |
| Plan            | `docs/tasks/YYYY-MM-DD-<issue-slug>-plan.md`                      | 구현 체크리스트, 변경 범위, 검증 명령, 커밋 범위 정리      |
| Troubleshooting | `docs/troubleshooting/YYYY-MM-DD-<issue-slug>-troubleshooting.md` | 문제 배경, 헷갈렸던 지점, 원인, 해결 과정, 검증, 한계 기록 |

`YYYY-MM-DD`는 작업일 기준 날짜를 사용한다. `<issue-slug>`는 이슈 번호와 핵심 주제를 포함해 kebab-case로 작성한다. 기존 관련 문서가 이미 있으면 새 파일을 늘리기보다 해당 문서를 갱신한다.

예시:

```text
docs/specs/2026-06-23-single-town-tab-duplicate-tab-spec.md
docs/tasks/2026-06-23-single-town-tab-duplicate-tab-plan.md
docs/troubleshooting/2026-06-23-issue-125-chrome-duplicate-tab-troubleshooting.md
```

---

## 3. Spec 작성 기준

Spec 문서는 구현 전에 작업 목표와 경계를 고정한다.

포함할 내용:

- 배경
- 목표
- 기대 동작
- 해결 정책
- 비범위
- 검증 기준

작성 규칙:

- 구현 세부보다 사용자 관찰 동작과 정책을 먼저 적는다.
- 비범위를 명시해 작업 범위가 커지지 않게 한다.
- 검증 기준은 수동 확인과 코드 검증을 모두 포함할 수 있다.

---

## 4. Plan 작성 기준

Plan 문서는 구현자가 바로 작업할 수 있는 체크리스트로 작성한다.

포함할 내용:

- 목표
- 체크리스트
- 구현 메모
- 검증 명령
- 커밋 범위

작성 규칙:

- 체크리스트는 `- [ ]` 또는 진행 후 `- [x]` 형식으로 관리한다.
- 변경 파일 범위를 명시한다.
- 커밋에 포함할 문서와 코드 범위를 분리해서 적는다.
- 로컬 검증용 테스트 파일을 커밋하지 않는 현재 관례가 있으면 커밋 범위에서 제외한다고 적는다.

---

## 5. Troubleshooting 작성 기준

Troubleshooting 문서는 작업 후 원인과 해결 과정을 남긴다.

기본 구조:

```markdown
# 이슈 N: 제목

작성일: YYYY-MM-DD
대상 이슈: 한 문장 설명

## 문제 배경

## 헷갈렸던 지점

## 원인 분석

## 해결 과정

## 검증

## 결과와 한계
```

작성 규칙:

- 기존 `docs/troubleshooting` 문서의 한국어 톤과 구조를 따른다.
- 단순 변경 목록보다 왜 문제가 생겼고 어떤 판단으로 해결했는지 남긴다.
- 자동화 검증과 남은 수동 검증을 구분해서 적는다.
- 해결하지 않은 범위나 한계를 마지막에 명시한다.

---

## 6. 커밋 기준

이슈 작업 커밋에는 관련 spec, plan, troubleshooting 문서를 함께 포함할 수 있다.

단, 다음 파일은 명시적으로 요청받지 않았다면 섞지 않는다.

- 다른 브랜치에서 남은 untracked 파일
- 로컬 검증용 테스트 파일
- 작업과 무관한 README, `.gitignore`, 임시 스크립트
- `docs/images`의 무관 스크린샷 또는 영상
